## 二、分支一 `backend/w2-health` —— B0.2

### 计划要求（仓库外开工计划的 B0.2 一节）

免登录端点；形状照 `contracts/registry.schema.json` 的 health 分支；`db / corpus / asset_rev / backup` 四项可读；10 路并发 < 100ms；禁 `model / model_status / model_endpoint / upstream / llm`。

### 实际变更

| 文件 | 内容 |
|---|---|
| `backend/app/core/health.py`（新） | 三个探针 `db_status` / `corpus_status` / `backup_status` + `aggregate_status` |
| `backend/app/api/system.py`（新） | 薄端点 `GET /api/health`：取 `asset_rev` + 四值聚合；**无任何 `Depends`**（免登录） |
| `backend/app/api/__init__.py` | +2 行（import + `include_router`） |
| `backend/app/core/db.py` | +`probe_readable()`（唯一建表入口 + 读一次） |
| `backend/tests/test_api_system.py`（新） | 8 条用例 |

### 实现方式上的四个决定

1. **探针不写在 `api/`**：门禁 `api_thinness` 要求 `api/**` 无 SQL、单函数 ≤ 40 行，SQL 只能落 `core/`。
2. **`db` 探针改道**：初版直接在健康模块里 `execute("SELECT 1")`，门禁 R-B 判「有 `execute()` 没 `commit()`」——没有加空 `commit()` 糊弄，而是把探针搬进本来就有 `commit()` 的 `core/db.py`。
3. **聚合规则写死一处**：`db≠ok` ∨ `corpus≠ok` ∨ `asset_rev=None` ∨ `backup=failed` ⇒ `degraded`；计划未定、本次补的一条是 **`never` 不降级**（"还没排过" ≠ "排了但坏了"），否则新环境永远红。
4. **`backup` 读不出来判 `failed`**（fail-closed）；时间戳不合 `…Z` pattern 时透传 `null`，避免产出违约响应。

### 达成

- 实跑 200：`{"status":"degraded","db":"ok","corpus":"missing","asset_rev":"f128ce1298f6","backup":{"last_success_at":null,"last_result":"never","last_failure_at":null}}`
- 用例覆盖：免登录、契约校验、禁字段缺席、`db=error`、`corpus=missing`、`backup` 三态 + 坏时间戳、`asset_rev=null`、单次 <500ms 病态守卫。
- **N20① 四次读数：90.3 / 76.9 / 81.6 / 67.7 ms，全部 < 100ms。**

### 缺谁配合

| 人 | 事项 |
|---|---|
| 人一 | 契约验收（贴 JSON + 命令即可）；跑**正式** N20（10 路**答疑**并发下，比 10 路 health 更紧） |
| 人一 | 定死"备份目录与 DB 目录同源"：health 读 `<DB 目录>/backups`，`backup.py` 用 `--data-dir`，默认一致、改环境变量会分叉 |

## 三、分支二 `backend/w2-tombstone` —— B2.1（+ C1.2 复核）

### 计划要求（仓库外开工计划的 B2.1 一节）

冻结墓碑格式；两条删除路径"删除前"写墓碑；幂等；审计；`deleteResult`/N15 文案声明边界；单测四类。

### 实际变更

| 文件 | 内容 |
|---|---|
| `backend/app/identity/tombstones.py`（新） | `record` / `load` / `mark_account_deleted` / `replay` / `log_path` |
| `backend/app/api/me.py` | 删除函数头部 +`record(...)`；`_DELETE_BOUNDARY` 补 7 天与重放 |
| `backend/app/api/admin.py` | 同理，`action=delete_user` |
| `backend/app/api/deps.py` | +`content_rev_best_effort()`（api 层替 identity 取 learning 的值，绕开依赖白名单） |
| `backend/tests/test_identity_tombstones.py`（新） | 11 条用例 |
| `test_api_me.py` +2 · `test_api_admin.py` +1 | 墓碑写入、写失败 503 且不动数据、管理员动作可区分 |

### 实现方式

- **存储定为旁挂 JSONL**（`<DB 同目录>/tombstones.jsonl`），不是第 8 张表：恢复会覆盖 `*.sqlite`，墓碑若在库里会被一起回滚——那正是"删除复活"的根因。
- **格式冻结 6 键**：`v / tombstone_id / user_id / deleted_at / action / content_rev`；不含 username、答案、哈希、令牌；按 `user_id` 幂等。
- **写序**：墓碑 → 取行数 → 硬删 → 脱敏 → 审计；**写失败即 503 且一行不动**（fail-closed）。
- **重放**用注入的 `purge`（`learning.store.delete_user_data`）：`identity` 的 import 白名单不许它引 `learning`。

### 与计划的偏差（主动交代）

1. **没有做成"同一事务"**：墓碑是文件，天然不参与 SQLite 事务；现有删除的两段 `commit` 在 `api/me.py` docstring 已被记为"可重试的合法中间态"，强行合并会把改动面扩到四个调用点。代价：崩溃在"已删数据、未脱敏"之间时靠下次重放补齐——**行为安全，事务性不是**。
2. **`deleteResult` 字段未加**：加字段会让现有 schema 校验当场变红，契约归人一。只落了 Plan B 文案（N15 `message` 现在带"备份最多保留 7 天；从备份恢复时会重放删除记录，已删除的账号不会复活"）。

### 达成

- 判据四项齐：删除、审计、逐表读回 0、重复删除幂等。
- 墓碑**不含内容与凭据**：用例直接读原始文本断言无 `prob_bayes_01 / 1/2 / 1/6 / 口令`。
- 实跑：删除后文件恰一行，`action=delete_own_data`、`content_rev=f128ce1298f6`。

### C1.2 复核结果

计划"补 3 条用例"，核查后发现 `test_api_chat.py:296` 已覆盖：200 契约体、404 非本人、404 未知 run、409 无挂起、409 非法动作、400 多余字段。**最终未加用例、未改代码**，只做签收。

## 四、分支三 `backend/w2-restore-replay` —— B2.3（+ B1.1 补强）

### 计划要求（仓库外开工计划的 B2.3 一节）

恢复后按墓碑重放：已删账号仍不可登录、四表仍 0；等人一 B2.2 的快照再汇合。

### 实际变更

| 文件 | 内容 |
|---|---|
| `scripts/backup.py` | import `replay` / `delete_user_data`；`run_restore` 恢复后先重放再读回；连接设 `row_factory=Row`；打印"[重放] …" |
| `backend/tests/test_scripts_backup.py`（新） | 4 条 CLI 级用例 |
| `backend/tests/test_asset_validation.py` | +2（多规则全列、唯一实现守卫） |

### 实现方式

- **不等 B2.2 就接**：`replay(paths=[backups_dir])` 把备份快照做成**可选来源**——没有快照时活日志够用（本机恢复），有快照时自动并集（换机恢复）。人一之后加轮转/快照不必回头改调用方。
- **`row_factory` 是实测才发现的坑**：`learning.store.count_user_rows` 按 `row["n"]` 读，而 `backup.py` 原本用裸 `sqlite3.connect`，不加这行 `purge` 会 `TypeError`。
- **用例直接跑脚本函数**（不只测 `replay()`），场景顺序与真实演练一致：**先备份 → 再删除 → 再恢复**。

### 达成

- 备份→删除→恢复后：四表全 0、账号 `deleted`、登录 401。
- 无墓碑的旧备份恢复**不误伤**（数据回来、账号仍 active）。
- 连跑两次恢复结果一致（演练会重跑）。
- `last_backup.json` 形状与 health 消费者一致。

### 缺谁配合

| 人 | 事项 |
|---|---|
| 人一 | B2.2：**7 天轮转**（现在完全没有）+ 把 `tombstones.jsonl` 复制为 `backups/tombstones-<stamp>.jsonl`；否则"换机恢复"分支不可演示 |
| 人四 | B2.4 独立见证 |
| 人三 | B4 验收与 squash merge |
