### 1.3 数据分级（★ 2026-09-16 重构：本表**只管"入仓与否"**这一个维度）

**重构原因**：原表把三个**正交维度**塞进一张表 —— **入仓与否** · **传输去向** · **删除与保留**，于是「外传」被写成与 L0/L1/L2 并列的**一级**。但 `student_qa_log` **同时是 L2 且会外传** —— 一张表表达不了"一物两属性"。现在按维度拆开：**本表管入仓**（§1.3）· **去向与删除见 §1.4** · **出网面见 §1.5**。

★ **二次修正（2026-09-16）：本表只承担"分级与入仓"，另两个维度降为索引列。**「保留与删除」给出该级的**处置口径**、「含外传字段？」给出该级**有没有外传面** —— 它们是**概览**，逐项的分工、去向与出网路径在 **§1.4 / §1.5**，**冲突以那两节为准**。原文写的是"本表只管入仓这一个维度"，却仍留着另两列 —— 那是**重构只做了一半**；而把这两列删掉反而会让 §1.3 无法自证"这一级会不会被删、会不会外传"。

| 级 | 内容 | 存放 | 入仓？ | 保留与删除 | 含外传字段？ |
|---|---|---|---|---|---|
| **L0** | 代码、契约、文档、**自制内容资产** | `content/`（顶层，与 `contracts/` 并列）+ 代码目录 | ✅ | git 历史 | ❌ |
| **L1** | **开放许可资源缓存**（预抓产物） | `backend/data/corpus/` | ❌ | 可随时重抓 / 删除 | ❌ |
| **L2** | **学生数据**：账号 · 令牌 · 审计 · 问答流水 · 提示流水 · 作答 · 掌握度 | `backend/data/*.sqlite` | ❌ **结构上不可能入仓** | **四类处置见 §1.4** | ★ **`qa_log` 含提问原文 ⇒ 是**（见 §1.5） |

> ★ **路径是"结构上不可能入仓"这句话的一半**：五类自制资产放**顶层 `content/`**，`backend/data/` 因此成为**纯运行时目录**（只装 L1 与 L2）—— 于是 `.gitignore` 可以对整个目录 **deny-by-default**，而不是靠"精确匹配库文件后缀"（旧仓的写法有个洞：`backend/data/*.sqlite` 里的 `*` **不跨目录**，库文件一旦挪进子目录就悄悄不被忽略）。
> ★ **"模型权重"已从 L1 删除（2026-09-16）**：原表把它与语料并列，与三处冲突 —— **N16** 明写"我们**不内置、不打包模型权重**"；**§1.5③** 的出网清单只有两个口，**没有任何口下载权重**；数 GB 权重也不可能"可随时重抓"。`ADR-0005` 的"被否决方案"里"内置 / 打包本地模型权重"同样已被否决。用户自备的本机模型是**用户自己的运行环境**，不是本项目的存放对象。
> ★ **已裁定（2026-09-16，负责人 · 决策 1A / §11.1-3）：v2 检索不使用嵌入 / 重排权重。** 旧仓的"混合检索"依赖 **BGE-M3 + bge-reranker-v2-m3** 的本地权重（数 GB），与三处硬约束冲突：**N16** 的"不内置、不打包模型权重" · **§1.5③** 的"**恰好两个出网口**"（没有任何口下载权重）· 本行对 L1 的收窄。**裁定 = 检索退化为纯词法**（BM25 + 中文 bigram），因此 **L1 只剩 `backend/data/corpus/` 一项**，`backend/data/models/` **不存在**。**代价（明账）**：F10 的检索质量下降（F10 是 SHOULD，其验收只要求"命中带出处 / 无命中如实说明"，**不承诺召回率**）。**若要恢复向量检索**，须走 ADR，并**为权重下载补一条出网口**（或把它并入 `scripts/fetch_corpus.py` 的预抓职责）。
> **L2 表的机械识别**：全部使用 `student_` 共同前缀，一条 `LIKE 'student_%'` 即可排除（沿用旧仓数据分级约束）。
> **前缀是数据分级口径，目录是代码归属口径** —— 两者严格分开，因此把存储层拆到 `identity/` 与 `learning/` **不会**破坏这条安全属性（ADR-0003 §5）。

**L1 语料的形状（必须约定，否则 F10 不可断言）**：
"语料不入仓"**不等于**"语料没有形状"。最小约定：

```
backend/data/corpus/<教材>/ch<nn>/sec<nn>.md     ← 路径即章节位置
    文件前置元数据（YAML front matter）：
        cite_id:    <教材>-<nn>-<nn>    ← ★ 出处的机器可读标识（F10 的验收对象）
        title:      第 3 章 条件概率
        chapter:    3
        license:    CC-BY-4.0           ← ★ 必填，且**必须在白名单枚举内**（见下）
        source_url: https://...         ← ★ 必填：来源可追溯
        fetched_at: 2026-09-16          ← ★ 必填：抓取时间
```

- **`cite_id` 是 F10 的验收对象**：检索响应必须带 `cite_id`，而不是一段自由文本的"出处" —— 否则"检索命中带出处"无法断言、也无法核对。
- ★ **只取开放许可资源**，`license` / `source_url` / `fetched_at` **缺一即为资产错误 ⇒ 启动报错退出**（与 §8-14 同一模式）。
- ★★ **2026-09-17 补：许可不是"有就行"，要过白名单与相容性判据**（原文只校验"三个字段在不在"，**不校验许可内容是否允许本项目这样用**）。**三条规则**：
  1. **白名单枚举**（`license` 的取值只能是这些）：`CC0-1.0` · `CC-BY-4.0` · `CC-BY-SA-4.0` · `public-domain`。**其余一律不收** —— 校验从"非空"升级为"**在枚举内**"。
  2. **`CC-BY-NC-*`（含最常见的 MIT OCW）单列，默认不收**：★ **实测确认（2026-09-17，抓 `ocw.mit.edu` 的条款页）**：**MIT OCW 的许可是 `CC BY-NC-SA 4.0`**，含 **Noncommercial**（不得用于商业目的）与 **ShareAlike**（衍生作品须同许可分发）两条硬义务 —— 而 `ADR-0004`/`ADR-0005` 把本项目定位为**可演进的正式服务**。★ 同页还有一节"Permitted Use of AI Training"：**用 OCW 内容训练 AI 须非商业、且衍生模型须同许可**。**因此：本项目若要收 OCW 语料，须先确认申报类别是创新训练（非商业）并走 ADR；否则不收。**
  3. **`SA` 与 `NC` 会传染**：内容资产若衍生自 SA / NC 语料（例如"从教材常见错误章节整理"的错因库），**衍生作品须同许可分发** —— 所以**"自制资产"的许可口径也要一并定**（本仓目前一字未提）。
- ★ **署名不是可选项**（2026-09-17 补）：`CC BY` 与 `CC BY-SA` 的 Attribution 义务是"**give appropriate credit, provide a link to the license, and indicate if changes were made**"（`CC BY-NC-SA` 同）。而本文 §1.5③ 的载荷白名单允许把**语料片段**随提问发往端点，界面上**只有 `cite_id`** —— **系统可以在完全不署名的前提下呈现开放许可内容，而所有门禁都是绿的**。⇒ **F10 的展示侧要求**（不在本节定门槛，属 `docs/01` F10）：出处**可点开**，显示 **来源名称 + 来源 URL + 许可名称（含许可链接）+ 是否改写**。
- **预抓 + 运行期只读缓存**：抓取在预抓阶段完成，运行期不联网取语料 —— 这样 `cite_id` 长期可复核（网页会变，缓存不会）。
- 缓存缺失时检索**如实说明"出处暂不可用"**（F10），**不得编造章节号**；并计入 §8 的失败模式。

### 1.4 数据存放分工表（★ 2026-09-16 新增 —— "什么存在哪里"的权威表）

**先定义参照物**（"本地"有三个意思，必须分开；此前**从未定义参照物**）：

| 名称 | 指什么 |
|---|---|
| **浏览器本地** | 学生**自己的设备**（`localStorage` / 内存 / HTTP 缓存） |
| **部署主机** | 跑 FastAPI + SQLite 的那台机器。**单机形态 = 教师 / 答辩本人的机器；远程托管形态 = 我们运营的服务器** |
| **第三方** | 用户配置的**远程**模型服务 |

> ★ **必须写死的一句话**：**"不外传"的准确含义是"不发往第三方模型服务"，不等于"数据不出学生设备"。**
> 单机形态下两者重合；**远程托管形态下两者不重合** —— 学生数据**存在我们的服务器上**（这正是 **N17 受控托管**存在的理由）。这是答辩现场最容易被追问的一处。

| 数据 | 存在哪 | 具体位置 / 字段 | 清除动作 | 需求 |
|---|---|---|---|---|
| 会话令牌（明文） | 浏览器本地 | `localStorage`；库里只存 sha256 | 登出 / 401 / 改密 / 禁用 / 删除 ⇒ 清 | F15 · N6 |
| **模型凭据（明文）** | 浏览器本地 | `localStorage`，固定键名，与账号绑定；**服务端不落任何介质** | 登出 / **切换账号** / 删除账号 / 改密 / 手动 ⇒ 清 | **N14** |
| **端点配置**（provider · model · base_url） | 浏览器本地 | `localStorage`，与凭据同生命周期 | 同凭据 | **N16** |
| **去向标记** `egress` | ★ **不落浏览器** —— 它是服务端**派生**的（按 §1.5① 的判据从端点配置算出来），落在 `student_qa_log` 行上 | `student_qa_log.egress` | 随账号脱敏 | **N15 · N16** |
> ★ **2026-09-17 改正**：本表原把 `egress` 列进"端点配置（provider · model · base_url · **egress**）"，而 §7.4 的 `dsh.endpoint` 只有三件套、`chat.schema.json` 的 `endpoint` 对象也 `additionalProperties: false` 只有三件套 —— 而**本表的规则 5 明写两处"必须同源"**。**`egress` 是派生的去向标记（N15 的判据），不是用户配置项**：用户配的是端点，系统算出去向；把它当配置项会让"设置页展示的去向"与"服务端记录的真实去向"变成两个来源（**R-N 的断言正是要比这两者一致**）。
| 界面位置（题目 / 提示层级 / 筛选 / 翻页） | URL | `#/practice?kc=&item=&hint=` | 不适用 | N11 |
| 跨页面临时态（当前 run、未提交作答） | 浏览器内存 | `core/store` | 刷新即丢（可接受） | — |
| 静态资源（katex 等） | 浏览器 HTTP 缓存 | 部署主机静态托管 | 浏览器自清 | N4 |
| 账号 · 令牌哈希 · 审计 · 问答流水（含提问原文）· 提示流水 · 作答 · 掌握度 | **部署主机 · SQLite** | `backend/data/*.sqlite`（七张 `student_` 表） | **四类处置**：四张数据表**硬删** / `token` **级联删** / `user` **脱敏** / `audit` **保留（只记 ID 与动作）** | F16 · F7 · F15 |
| **告知已读标记** | **部署主机 · SQLite** | `student_user.notice_ack_at`（存服务端的理由：**换设备仍须告知**） | 随账号脱敏清空 | **N15** |
| 开放许可资源缓存（预抓产物） | 部署主机 · 文件系统 | `backend/data/corpus/`（不入仓） | 可随时重抓 / 删除 | F10 |
| ★ **备份产物** | **部署主机 · 文件系统** | `backend/data/backups/` —— **同一台主机的另一个卷 / 目录**，仍在 `backend/data/**` 的 deny-by-default 内；**不含日志**（R-O） | 按保留策略轮转覆盖 | **N19** |
| **运行日志** | **部署主机 · 文件系统** | **`backend/data/logs/`**，轮转 10MB × 5；**内容受 R-O 约束** | 轮转覆盖 | N14 · N16 |
| 契约 · 五类内容资产 · 代码 · 文档 | 仓库 | `contracts/` · `content/` · `backend/` · `docs/` | git 历史 | F20 |
| **提问原文 + 上下文**（仅 P2 远程端点） | **第三方**（不在我们控制内） | 随请求发往远程端点；`qa_log` 只记 `provider` / `model` / `egress` | **删不掉** —— 须与 N15 一并告知 | **N15 · N16** |

**表后三条规则**：

1. ★ **R-O · 日志与审计只记 ID 与动作，不记内容**：不得出现提问原文、学生答案、教材片段、凭据。**理由**：F16 靠"读回 0 行"验收，而**日志文件不在读回清单里** —— 内容一旦进日志，"删除"就只删了数据库那一份。这是原设计里**唯一一个"验收通过但数据仍在"的洞**。
2. **日志目录定死为 `backend/data/logs/`**（此前全仓无日志位置），落在 `backend/data/` 的 deny-by-default 之内，`.gitignore` 既有规则即可覆盖。
3. **凭据与端点配置同生命周期**；**凭据不随令牌撤销而失效**（它是用户的额度，不是我们的会话），但**登出必须清除**（保护"下一个人"）。
4. ★ **备份不构成第三个出网口（N19）**：备份**只落部署主机本地**（另一个卷 / 目录），**不写对象存储、不写异地** —— 否则 §1.5③ 的"恰好两个口"就不成立。**异地 / 多副本备份列为不做**，放开必须走 ADR。
5. ★ **凭据的"五条清除动作"以本表为准**（登出 / 切换账号 / 改密 / 禁用 / 删除 / 手动）—— 前端的键名与清除动作表见 §7.4，两处必须同源。

**四条设计规则**：

1. **ID 稳定且可引用、不得复用** —— 被历史记录长期引用的 ID 一律适用此规则，**不只知识点**：
   - `kc_<slug>`（知识点，如 `kc_bayes`）
   - `prob_<slug>`（题目，被 `attempt.item_id` 引用）
   - `pt_<slug>`（题型，被题目与 F17 的 `model_id` 引用）
   - ★ **`mp_<slug>`**（**错因条目**，被 `attempt.mistake_id` 引用 —— 见 §3.2）
   - ★ **`fm_<slug>`**（**公式 / 定理条目**，被 F18 的检索响应引用）
   改含义只能**新增 ID** + 把旧的标 `deprecated`，否则历史作答的标注会指向**错误含义**（而且无法事后区分哪些是错的）。
   ★ **两个前缀是 2026-09-16 补的**：§3.2 的 `mistake_id` 早已写"`mp_<slug>`，**见 §2.2**"，而 §2.2 只定义了三个前缀 —— 那是一个**指向不存在内容的引用**；`fm_` 则从未定义，而 F18 要"按名称返回**唯一条目**"，没有稳定 ID 就只能靠名称字符串。
   ★ **适用范围已扩（2026-09-16）**：本规则原文限定为"被**历史记录**引用的 ID"，实际更宽 —— **凡被契约、资产或历史记录引用的 ID 一律适用**（`mp_` 被 `attempt` 引用、`fm_` 被检索响应引用，两者都不属于"历史记录"）。
2. **无环是硬约束**（F19 验收）：建图时做拓扑排序，有环即拒绝加载（不是警告）。加载失败必须**报错退出**，不得静默丢边。
3. **边有含义**：`depends_on`（前置）单向。上溯（F9）沿 `depends_on` 反向走。★ **上溯的门槛已裁定（2026-09-16，决策 6A / §11.1-8）：不设门槛 —— 全量返回 + 计数。** 输出 = 从该知识点的错误作答出发、沿 `depends_on` **反向可达**的前置知识点集合（**同一条路径不得重复计数**）；界面**全量显示**并给出计数（"沿依赖上溯到 N 个前置知识点"），**不按错题数或层数截断** —— 门槛属学习者建模（`docs/01 §9` 不做），而"只显示前 2 层"这类截断会让 F9 的"上溯到根源"**失去判据**。集合为空时显式说"未定位到前置薄弱点"。
4. **题目与题型都挂知识点**，但两者独立：一道题可以考多个知识点；一个题型可以服务多个知识点。

> **已考虑并否决的替代方案**：① 删除时一并清除 `target_id` 指向该用户的行 —— 否决，因为"该生数据曾被反复查看"这件事会变得不可查，而它恰恰是监督的价值所在；② 对 `target_id` 做盐化 —— 否决，为一条**落在我们控制范围内**的审计记录引入一个密钥管理面不划算。
> **代价（记账）**：删除后仍存在"某个匿名 ID 曾被查看过"的记录。这是**有意选择合规证据优先于彻底清除**，若日后合规要求变化，改法是上面被否决的方案 ①。

**新增 `asset_version` 的理由与合规性**：
F7 要求"**标准答案快照 + 资产版本号**"。`expected` 已提供快照，但快照离了版本号**无法解释**——题库改版后，"当时的标准答案"为什么是这个值、知识点标注依据的是哪一版 DAG，都查不出来。
**这是"只增不改"允许的增量变更**：新字段可空、有默认值、不改变任何既有字段的含义，旧数据读出来是 NULL 而非错误。

**`kc_ids` 非空的实现路径（F19）**：
不是"在写入时校验一下"这么弱 —— 而是**从源头保证**：F20 要求**题库条目必须关联知识点 ID**，而 `attempt.kc_ids` 由题目继承。因此：

```
题库条目 kc_ids 必填（F20）
        └─▶ 作答时继承 kc_ids
                └─▶ attempt.kc_ids 天然非空（F19）
```

三层都要有断言：① 题库加载时校验条目 `kc_ids` 非空；② 契约里 `kc_ids` 标 `minItems: 1`；③ 写入函数拒绝空数组并抛错（**不得静默写 `[]`**）。
> 为什么强调第三层：旧仓该列是 `NOT NULL DEFAULT '[]'` —— **"非空"在数据库层面看起来被满足了，实际存的是空数组**。这正是 F19 要防的那种"表面合规"。

#### `student_mastery` —— 聚合口径

| 字段 | 说明 |
|---|---|
| `user_id` + `topic`（PK） | `topic` **就是知识点 ID**（与 `attempt.kc_ids` 同口径，不再另设一套命名） |
| `attempts` / `correct` | 聚合计数 |
| `updated_at` | 最后更新时刻 |

**更新时机**：**每次作答后累加**（同事务）；**`correct` 为 NULL 的作答（不可判定）不累加**。
**不做**"重算全表"——重算会在删除时产生漂移。

**★ 多知识点聚合口径（必须写死，否则数字会虚高）**：一道题可以挂多个 `kc_ids`，一次作答会对**所有** topic 各累加一次 `attempts` / `correct`。因此：

- **进度视图的"总作答数"必须按 attempt 去重**（`COUNT(DISTINCT attempt_id)`），**不得对 `mastery.attempts` 求和** —— 否则同一份作答被重复计入，总量虚高；
- **"首次正确率"的单位是 `(user, item)` 的第一次 attempt**，不是 `(user, topic)` 的第一次 —— 后者在一题多知识点时无定义。

**已知限制（诚实）**：当前口径是**计数**，不含"提示次数对掌握度的扣减"。F6 要求如实记录，但**掌握度公式本身不在 v2 范围内**（属学习者建模，`docs/01 §9` 不做）。数据齐备，公式后补 —— 这正是"现在开始记"的意义。

#### 其余几张表
`student_user` / `student_token` / `student_qa_log` / `student_hint_log` 的字段沿用已落地实现（`student_hint_log` 为 v2 新增，字段见 §3.1；`student_qa_log` 的增量见上表）；`student_audit` 同理。**字段级机器可读定义在 `contracts/`（A3）**，本篇只记录**本仓的增量**（`asset_version` · `correct` 可空 · `grader` 新增取值 · **`qa_log.provider`/`model`/`egress`** · **`user.must_change_pw`** · **`user.notice_ack_at`**）与口径说明。

★ **`student_user.must_change_pw`（2026-09-16 补位）**：由 §6.1 的"管理员重置密码"引入 —— 置位后**只放行 `POST /api/auth/password`**，其余学习类接口一律 **403 `must_change_pw`**（**不复用 `forbidden`**：那个 code 的语义是"角色不足"，混用会让前端把"去改密码"显示成"无权访问"）。字段级定义在 A3 契约；**它此前只在 §6.1 出现一句，既不在本节的增量清单、也不在 §3.4 对照表、也没有状态机条目**（见 §5.3）。

### 3.3 内容资产：五类、格式与版本化（F20）

| 资产 | 最小规模（首版**下界**） | 必须关联 | 主要消费方 |
|---|---|---|---|
| 题库 | **≥ 30 道**（长期目标 ≥ 100 道，与评测资产共用） | 知识点 ID · 题型 ID · **`gradable` 标记** · ★ **`answer_kind` 标记**（枚举 **`value`** / **`text`**，与 `gradable` 并列；**任一未标记视为资产错误 ⇒ 启动报错退出**，与 §8-14 同一模式）。★ **两者关系写死（2026-09-16）**：`gradable=false` ⇒ **不进判定链**（`correct=NULL` · `grader=not_gradable`，见 §4.3②），`answer_kind` 不参与；**`docs/01 §6` 的"判定准确率"与"判定延迟"只对 `gradable=true` 的题目统计**，"数值题 / 应用题"= `answer_kind` 的 `value` / `text` | 刷题 · 评测 |

| 知识点 DAG | **≥ 40 节点且覆盖 ≥ 5 章**，拓扑无环 | —（节点即 ID） | F9 · F19 · 上溯 |

| 题型与解法套路 | **≥ 15 类** | 知识点 ID | **F17 的"适用模型"** |

★ **`answer_kind` 为什么必须在这里写出来（2026-09-16）**：`docs/01` 的 **F20**、**§6 的"判定准确率"与"判定延迟"两条验收**、以及**附录 C** 都引用了它（`answer_kind=value` / `answer_kind=text`），而**本篇此前全篇没有这个词** —— 于是两条验收读不到自己声明的分类字段，F20 的"题库条目必须带 `answer_kind`"也**没有落点**。

**五条规模下界都是下界，只许上调**（与地板阈值同一精神；公式库 ≥ 30 条为 2026-09-16 补入）。

**存放路径（唯一）**：`content/<asset>.json` —— **顶层目录，与 `contracts/` 并列**。理由：五类资产是**项目级真相**（自制、入仓、可 diff、可 review），而 `backend/data/` 从此是**纯运行时目录**（只装 L1 语料与 L2 库）。把"必须入仓"的东西放进"绝不能入仓"的目录里，会让 §1.3 那句"结构上不可能入仓"变得难以一眼自证。

**统一版本化规则**：

1. 每类资产一个文件（或一个目录 + 索引），**文件头带 `rev`**：`<asset>-<YYYY.MM.DD>.<n>`。
2. 生成物 **`content/MANIFEST.json`（入仓）** 记录**五类资产各自的 rev**，并派生出**组合版本号** `content_rev`。★ **算法已定死（2026-09-16，决策 4B / §11.1-6）**：五类资产**按 ASCII 键名升序**排列，逐个拼成 `key=rev`，以 `;` 连接，取 `sha256(...).hexdigest()[:12]` —— 即 `content_rev = sha256("dag=<rev>;formula=<rev>;mistakes=<rev>;problems=<rev>;types=<rev>")[:12]`。★ **本式同时把五类资产的键名固定下来**：`content/problems.json` · `content/mistakes.json` · `content/dag.json` · `content/formula.json` · `content/types.json`（键名进哈希，**不能随手改**）。★ **两个设计点各有一个理由**：**顺序写死**是因为"按**中文名**排序"会依赖 locale —— 同一份资产在不同机器上可能算出**不同的 `content_rev`**，于是 F7 的版本号不可复现；**用哈希而不是直接拼接**是因为 `attempt.asset_version` 要长期存（F7），12 位十六进制比一串 rev 更稳定地短。★ **反解链不受影响**（见第 3 条）：哈希不可逆，因此反解是"**在 `git log` 里找计算出的 `content_rev` 相同的那一版 MANIFEST**"，再落回五类 rev —— 这一步**可算、可核**，所以第 3 条的"反解链依赖 MANIFEST 入仓 + git 历史"依然成立。
3. `attempt.asset_version` 存**当时的 `content_rev`**；**反解链**：`content_rev` → 同提交的 `content/MANIFEST.json` → 五类资产各自的 `rev` → **`git log` 里升该 rev 的那次提交**（内容与解释一并可查）。
   > 反解**依赖 MANIFEST 入仓 + git 历史**这两件事同时成立。若 MANIFEST 不入仓，旧 `content_rev` 就是一个无法解释的数字 —— 那正是 F7 要防的事。
4. **`rev` 变更即视为内容变更**：改一个错因解释也要升 `rev`。**不允许原地改内容不升版本** —— 否则历史记录的解释链断裂。
5. **一致性由启动校验守住**：资产文件头 `rev` 与 MANIFEST 不一致 ⇒ **启动报错退出**（与 §8 第 14 条同一模式），防止"手改了资产忘了重生成 MANIFEST"静默产出错版记录。

> 资产**入仓**（L0，自制、可版本化、可 diff、可 review）；**教材语料不入仓**（L1，见 §1.3）。
> 这与 N3 不冲突：入仓的是我们自编的题目、错因、DAG、公式、题型；从教材摘录的原文属 L1。

### 3.6 并发与事务（R-B 的落地）

| 规则 | 做法 | 为什么 |
|---|---|---|
| 并发写 | 开启 **WAL** + `busy_timeout=5000` | 读写不互相阻塞；短时争用自动重试而非立即报错 |
| 建表 | **只有一个建表入口**，幂等 | 分两处建表必出"某个入口漏建了表"，症状是运行时的 `no such table` |
| 写事务 | 每次写**显式 `commit()`**，并集中在一个 `with closing(conn)` 里 | 旧仓真实 bug：写函数漏一次提交，作答记录被**静默回滚** |
| 复合写 | `作答 + 掌握度 + 提示流水的计数读回` 的联动写在**同一事务**内（★ **口径修正（2026-09-16）**：`attempt.hint_used` 是**派生值**，原文"提示计数读取"读起来像在更新一个存量计数） | 否则会出现"记了作答但掌握度没动"或"用了 3 次提示但记成 2 次"的半成品状态 |
| 测试 | **必须读回断言**，不得只断言"HTTP 200" | 同上的 bug 当时没被发现，就是因为测试只看了状态码 |
| ★ **备份取快照**（N19 的机制，2026-09-16 补） | 开了 **WAL** 之后，备份**不得用文件级 `cp`**（会漏掉未检查点的 WAL 页 = "备份成功但少了最近的作答"）—— 必须用 **`sqlite3.Connection.backup()`**（Python 3.7+，与"stdlib `sqlite3`、无 ORM"一致）或 `VACUUM INTO` 产出**一致快照** | F16 靠"读回 0 行"验收、N19 靠"逐表读回"验收；**文件级拷贝会让 N19 平凡通过**（文件在、内容缺），与"写库漏提交"是同一类事故 |

## 4. 三条主链路

### 4.1 登录与令牌链路（F15 · N6）

```
浏览器                        后端                         SQLite(L2)
  │                            │                              │
  │ POST /api/auth/login       │                              │
  │ {username, password}       │                              │
  ├───────────────────────────▶│                              │
  │                            │ ① 查 user                    │
  │                            ├─────────────────────────────▶│
  │                            │ ② 不存在 / 已删除 / 空哈希？  │
  │                            │    ⇒ burn_time() + 401       │
  │                            │ ③ bcrypt.checkpw             │
  │                            │    失败 → failed_count+1     │
  │                            │    达上限 → 置 locked_until  │
  │                            │    且**校验失败也烧时间**     │
  │                            │    ⇒ 401（或 423，见下）      │
  │                            │ ★ ④ 锁定中？→ 423            │
  │                            │ ★ ⑤ status=disabled？→ 403   │
  │                            │ ⑥ secrets.token_urlsafe(32)  │
  │                            │    库里只存 sha256(明文)      │
  │                            ├─────────────────────────────▶│
  │ {token, expires_at, user}  │◀─────────────────────────────┤
  │◀───────────────────────────┤                              │
  │                            │                              │
  │ 后续请求：Authorization: Bearer <token>                    │
  ├───────────────────────────▶│ resolve_token(sha256)        │
  │                            │ → revoked/过期/账号禁用 ⇒ 401/403
```

> ★ **③④⑤ 的次序是刻意的**：**锁定与禁用的判定都在密码验证之后**。
> 反例（旧仓实测的次序）：把"锁定中 → 423"放在验证**之前**，则"不存在的用户名"给 `401`、而"已锁定账号"给 `423` —— **无需密码即可区分**，构成账号存在性枚举面。旧仓的禁用检查本就在验证之后（这点是对的），是本篇先前把图画错了，已按实现改正。

**七条口径（每条都对应一个具体的坏结果）**：

| # | 口径 | 不做会怎样 |
|---|---|---|
| 1 | **服务端会话令牌，不是 JWT** | JWT 无状态 → 无法满足"停用账号**立刻**生效" |
| 2 | 库里**只存 sha256**，明文只在登录响应出现一次 | 库被拿走等于所有会话被劫持 |
| 3 | 令牌 **7 天**有效，可即时撤销（`revoked`） | 无法响应"这孩子手机丢了" |
| 4 | **改密码 / 禁用 / 删除 ⇒ 撤销该用户全部令牌** | 改完密码旧令牌还能用，等于没改 |
| 5 | 失败 **5 次锁 60 秒**；**校验失败也烧固定时间** | ① 可无限爆破 ② 通过响应时间可枚举用户名是否存在 |
| 6 | 除 `health` / `login` / 静态资源外，**全部端点要求登录** | **A1 已裁决：不设免登录例外**（理由见 `docs/01` §1） |
| 7 | 管理员账号**只能由 CLI 创建**，接口不可创建管理员 | 否则拿到一个管理员令牌就能自我复制 |

> ★ **信息量不变量（可断言）**：**在密码通过之前，一切失败都返回同一个 `401 bad_credentials`，且都烧等长的时间。**
> 因此"账号已被禁用（403）""尝试次数过多（423）"这两个可区分的状态，**只可能在密码验证通过之后出现**。这条不变量是 §6.3 两个 `code` 拆分成立的前提，也是它唯一的正当性依据 —— 测试直接断言它。

### 4.2 答疑链路（SSE · F1 F2 F3 F10 F13）

```
POST /api/chat  { query, context }        ← 必须登录（F15）
   │
   ├─ ① 校验：query 长度上界（R-A）· context 可缺省但显式降级（F1）
   ├─ ② 落 qa_log（提问原文，L2）—— 先落再答，保证"问了就算数"
   │
   ▼  graph（LangGraph 图运行时）
   ├─ 路由 → 意图（solve / explain / lookup / visualize）
   ├─ 检索（本地语料）→ 命中带出处；**无命中如实说明**（F10 · N2）
   ├─ 求解 → 逐步过程，每步 {说明, 式子}（F2 结构断言，**仅 solve 类**）
   ├─ 验证 → **验证报告**（级别 A–D + 逐项检查 + 置信度）—— 每条解答必带（F3）
   │      ├─ 通过 → 正常输出
   │      └─ ★ **不通过** → 重算一次（**上限 1 次**）
   │             ├─ 重算后通过 → 正常输出
   │             └─ 仍不通过 → **标 `uncertain`** + 级别降 **D** + 事件流**显式告知**
   │                             （附"哪一项检查没通过"）—— **不静默输出，也不假装通过**
   ├─ 需要人协同？→ hitl.request（挂起，等前端确认）
   └─ 汇总 → 事件流
   │
   ▼ SSE 帧（`events.schema.json`）
   │   frame: { seq, type, ts, payload }   seq 单调递增
   ▼
前端消费：seq 去重 · 按类型渲染 · **断流后重新发起（见硬性设计 1）** · 不重放已渲染帧
```

**八条硬性设计**：

1. ★ **`seq` 只用于去重，不承担"断流续传"（2026-09-16 修正）** —— 服务端**不做重放缓冲**，断流语义为"**重新发起（会重跑一次图）**"。**已记账：因此不能续传**。理由：内存环形缓冲在单 worker 下能工作，但要为"断流"引入一套会话态生命周期，而 v2 的 SSE 是**短连接**（一次答疑一次流），收益与复杂度不成比例。若将来改做缓冲，须走 ADR。
2. **客户端断开 ⇒ 图必须取消**。否则一次刷新页面会留下一个还在跑的后台图，把单 worker 拖死。
3. **验证报告缺失即不出结果**（F3："无标签不出结果"）—— 这是 N2 的机制，不是前端的事。
4. ★ **验证不通过有明确出口**（本轮补齐）：**重算一次（上限 1 次）→ 仍不通过就标 `uncertain` 并降级到 D ＋ 显式告知**。
   这是 **N1 的机制所在** —— N1 的验收是"注入的已知错解被拦住或标注"，而"拦住"就发生在这一步。没有这一条，N1 只是一句指标，没有对应设计。
   ★ **"重算"的语义已写死**：**换一条策略重新求解**（多路求解的第二次尝试），**不是**同一次调用的重试采样 —— 同一次调用的多个样本会共享同一个错误前提。上限为 1 次：无限重算会把"验证"退化成"直到算对为止"。**"哪些检查项的什么结果算不通过"见 §4.4 的判定表。**
5. **`hitl.request` / `hitl.resolved` 必须成对**，且前端必须有可见的挂起态 —— 否则用户面对一个永远不动的进度条。
6. **上下文来源可替换**（N12）：`context` 是一个**显式可选参数**，不是"从浏览器读屏"。将来探针接入时，它只是换一个来源，**契约不变**。
7. ★ **F2 的结构断言有明确落点**：解答步骤以 **`steps[]`** 出现在两处 —— ① SSE 的解答事件（`events.schema.json` 里承载步骤数组的那个字段）② **`GET /api/runs/{id}` 的响应**（`steps: [{说明, 式子}]`，★ 该端点此前**不在 §6.1 的路由清单里**，2026-09-16 补入）。**断言的对象是这两处**，不是"事件流里大概有步骤"。仅约束 **solve 类**解答 —— 路由枚举的四个意图（`solve` / `explain` / `lookup` / **`visualize`**）里**只有 `solve` 是解答**，其余三个不受"步骤数 ≥ 3"约束（`visualize` 原未列入排除项，2026-09-16 补）。
8. ★ **答疑链路的同步 CPU 工作一律 `to_thread`（2026-09-16 补，N20 连带）**：判定链早有这条（§4.3-1 · §8-7），**答疑链没有** —— 而 N20 承诺的是 **10 路并发答疑**。图运行时里的同步部分（求解 / 符号计算 / 语料检索）若占住事件循环，10 路并发会退化成串行，`/api/health` 也会跟着变慢（§8-7 的断言会当场失败）。**判定 / 答疑两条链路的同步工作都必须丢线程池**，这是 N20 ④ 的前提。

### 4.2.1 答疑的前置条件（N14 —— 无凭据则不可用）

```
有凭据 + 端点在信任范围内 → 走上面的链路
无凭据                   → ★ 503 `model_key_missing`   （引导去设置页填凭据）
端点不可达 / 超时 / 被拒绝 → ★ 503 `model_unreachable`   （**可重试**，**不得引导填凭据**）
凭据无效 / 被撤销         → ★ 400 `model_key_invalid`   （客户端可修的输入问题）
额度不足 / 欠费           → ★ 402 `model_quota_exceeded`
                          → 四者一律**不发起、不降级、不产出假答案**
                          → 判定 / 错题本 / 进度 / 知识图谱**全部照常可用**（它们不依赖模型）
```

> **为什么连 mock 都不留**：旧仓的 `llm_provider = "auto"`（无 key 走 mock，保证零配置可跑）是**产品模式**，与 **N2 诚实**直接冲突 —— mock 产出的是**假答案**。v2 只在**测试**里注入假 provider，**不提供产品级 mock**。这条要写死，否则会有人把 mock 重新加回来。
> ★ **为什么"未配置"与"不可达"必须分成两个 code（2026-09-16）**：`ADR-0005 §5` 已裁定拆分，而本节与 §6.3 此前仍是合并的 `model_unavailable`，前端行为被写成"显示'未配置模型凭据'并提供 `#/settings?tab=model` 入口" —— 于是**断网的学生被推去填 key**（他会反复重填一个本来就正确的凭据），而真正该做的是"重试"。这两个状态的**用户动作完全相反**，因此不能共用一个 `code`。
> **凭据怎么传**：请求头 `X-Model-Key`（**不放 body**，避免进 body 日志）；因此答疑**必须用 `POST + fetch 流`** —— `EventSource` **不能带自定义头**。若将来改用 `EventSource`，凭据必须改走 cookie 或 body（已列为失败模式，见 §8）。
> ★ **P1（本机端点）下的空凭据（2026-09-16 补）**：本机端点**没有真实凭据**，因此 `X-Model-Key` **允许为空串**（仅 P1 单机形态）；此时 `egress='loopback'`，N15 文案为"数据不发往第三方"。**空串同样受 R-M 约束**（不得落日志 / 审计 / 错误信息 / URL / 载荷本体）—— 这一条是 N16 验收① 断网演示的前提，此前无落点。

#### 端点信任边界（N16 · `ADR-0005 §4` —— 2026-09-16 落进正文）

**端点由用户提供（N14），因此服务端会向一个用户可控的 URL 发起请求 —— 这是一个真实的 SSRF 面。** 六条规则，**`/api/model/ping` 与 `/api/chat` 必须共用同一个校验函数**（否则"用 ping 绕过校验再直接用 chat"就是一条现成的旁路）：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **预置供应商白名单**（DeepSeek / Qwen / GLM + 自定义 OpenAI 兼容），自定义时仍须过第 2–4 条 | 只靠"用户填什么就是什么"等于把出网权交出去 |
| 2 | ★ **loopback 例外仅在单机形态**，且**必须由部署者显式勾选**才生效（与 N18 的"单机允许 http"**共用同一开关**） | 远程托管下学生填的 loopback 是**服务器**的 loopback：他既无正当性使用它，它又是一条通往服务器内部服务的路 |
| 3 | ★ **强制 `https`**（单机 loopback 例外）；★ **禁 RFC1918 / 169.254.169.254 等内网与云元数据地址** | 只挡 loopback 不够：`10.0.0.0/8`、`192.168.0.0/16`、**云元数据端点**都是同一类目标，而元数据端点能直接读出托管环境的凭据 |
| 4 | **禁跟重定向** | 否则第 2、3 条可以被一个 302 绕过去（校验的是第一个 URL，请求最终落在另一个地址） |
| 5 | **超时与响应体上界**（连接 / 读取超时 + 最大响应字节） | 用户可控的端点可以让服务端一直挂着 —— 单 worker 下这就是一次拒绝服务 |
| 6 | **校验失败一律 503 `model_unreachable`**（不回显解析到的 IP、不回显内部错误） | 把"这个地址被拒绝"与"这个地址不可达"**对外合并**，避免把内网探测结果回吐给用户 |

> ★ **这六条此前只在 `ADR-0005` 里有，本篇零落点**（2026-09-16 补）。ADR 是决策记录，**执行面必须在正文**，否则实现只看本篇就得到"只挡 loopback"这一条。

### 4.3 刷题判分链路（F4 F5 F6 F7 F8 · N1）

```
GET  /api/problems?kc=...&limit=&cursor=      ← 题目来自内容资产（F20）
     ★ **响应绝不包含 `expected` / 解析 / 错因答案**（见下"暴露面")
POST /api/practice/hint                        ← ★ 提示阶梯的唯一推进口（F6）
     { item_id, session_id }
     → { level, content, hint_used }           ← hint_used 由服务端计数后回传
POST /api/practice/grade
     { item_id, answer, duration_ms, session_id }
     ★ 请求体里**没有** hint_used / attempt_no —— 两者都由服务端派生
   │
   ├─ ① 参数校验：answer **max_length=200**（R-A）· 数值上界
   ├─ ② 读 `gradable`（F20）：为假 ⇒ **显式降级**
   │      → 200 { graded: false, reason: "not_gradable", message: "该题需人工判定" }
   │      → 仍写 attempt，但 correct=NULL、grader='not_gradable'、**mastery 不累加**
   ├─ ③ 归一化（domain 纯函数）：去空白 / 统一符号 / 精度口径
   ├─ ④ 判定（domain 纯函数，**不依赖 LLM 往返**，F4）
   │      ├─ 正确 → correct=1
   │      └─ 错误 → 错因匹配（吃错因库，F5）
   │            命中 → 输出对应错因解释
   │            未命中 → **如实说"未识别错因"**，不得编造
   ├─ ⑤ 定级：本判定为**确定性**，验证级别按手段封顶（附录 C）
   ├─ ⑥ 服务端派生（★ 权威值，不读请求体）：
   │      hint_used  = COUNT(student_hint_log WHERE user,item,session)   ← F6
   │      attempt_no = COUNT(student_attempt WHERE user,item) + 1        ← F8 · F11
   │
   ├─ ⑦ **同一事务**写入：
   │      attempt（含 expected 快照 + asset_version + created_at）  ← F7
   │      mastery（(user_id, topic) 累加；correct 为 NULL 时跳过）    ← F11
   │      显式 commit()                                             ← R-B
   ▼
GET  /api/me/wrong?kc=...&limit=&cursor=      ← 跨会话读回（F8）
GET  /api/me/progress                          ← 进度 / 薄弱（F11，数据源=attempt）
```

**六条硬性设计**：

| # | 设计 | 对应 |
|---|---|---|
| 1 | 判定**全部走确定性代码**，且是**同步 CPU 工作 ⇒ 必须丢线程池** | F4 · **旧仓 P0 事故**：`/api/practice/grade` 曾冻结整个事件循环 |
| 2 | 判定正则**禁止嵌套量词**；对长数字串有专门测试 | R-A · 旧仓实测：100k 位数字耗时约 2 分钟 |
| 3 | 提示分级由**独立接口**推进，**每次调用写一条 `hint_log`**；`hint_used` 由服务端计数；**未提交前不返回完整解析**（完整解析只在 `grade` 之后可取） | F6 · §5 伦理约束 |
| 4 | 判定接口**只读题目、不写题库**；内容资产是只读的 | F20（资产一致性） |
| 5 | ★ **列表接口的答案暴露面必须封死**：`GET /api/problems`（以及任何列表 / 详情接口）**不得返回** `expected`、解析步骤、错因解释或任何能反推答案的字段 | **§5 伦理约束在 UI 之下同样是敞开的** —— 只要列表接口带标准答案，前端不显示就只是"没做"，谁都能直接读接口 |
| 6 | ★ **`hint` / `answer` / `attempt_no` 的权威都在服务端**：URL 里的 `hint` 层级只用于渲染；改 URL 不能让服务端认为已取过提示；请求体里传 `hint_used` 会被**忽略**（不是报错，避免旧客户端崩），但**不采信** | F6 · §5 |

★ **`POST /api/practice/grade` 的响应里必须有 `solution`（2026-09-16 补位）**：§4.3-3 与 §5.2 都写死"**完整解析只在 `grade` 之后可取**"，但此前**全篇没有说明解析从哪来** —— 提示阶梯的最后一格因此没有出口。响应形状（字段级定义在 A3）：

```
{ graded, correct, score, mistake_id, mistake_matched,
  hint_used, attempt_no,
  solution: { steps: [{说明, 式子}], cite_id: <string|null>, explanation } | null }
```

**`solution` 只在本次请求确实写入了一条 `attempt` 之后才非空** —— 不可判定题目（§8-18）、参数校验失败、未登录时为 `null`。这条把"未提交前不返回完整解析"从**前端纪律**变成**接口事实**。

### 4.4 验证判定表（★ 2026-09-16 新增 —— `§4.2-4` 指向的就是本表，也是 N1 的机制所在）

`§4.2-4` 写"验证不通过 → 重算一次 → 仍不通过就标 `uncertain` 并降 D"，但**"什么算不通过"全篇没有定义** —— 于是 **N1**（唯一的技术差异化，MUST）的"拦住"判据没有载体，`docs/01 §6` 的"诚实性"与"错误拦截率"两条验收同时悬空。本表把它写死。

**① `level` 的取值与 `cap(level)`** —— 置信度上限表，同时也是 `docs/01` 附录 A 的待落地项（**B 级在这里补齐**）：

| level | 含义 | 可达条件（**手段封顶**） | `cap(level)` |
|---|---|---|---|
| **A** | 纯数值，可完全验证 | `checks` 里**必须出现** `sympy_recompute` | **1.0** |
| **B** | 符号可强验证 | `checks` 里**必须出现** `symbolic_equivalence` | **0.90** ★ |
| **C** | 应用题，可交叉验证 | `checks` 里**必须出现** `cross_check` 或 `unit_check` | **0.85** |
| **D** | 证明题 / 开放题，**不做承诺** | **无条件可达**（兜底级） | **0.4** |

- ★ **B = 0.90 是 2026-09-16 补的**：旧仓 schema 只定义了 A / C / D，**B 没有上限** ⇒ `docs/01 §6` 的 `conf ≤ cap(level)` **全量断言无法执行**（一条无法执行的 MUST 断言）。取值理由：它**必须低于 A 的 1.0**（符号等价性判定本身有实现风险，弱于数值重算），且**高于 C 的 0.85**（符号等价是**强验证**，不是交叉印证）—— 0.90 使三档严格单调。
- **两条断言都执行**：`level ≤ 手段允许的上限`（挡"一个手段都没跑却报高级别"）**且** `conf ≤ cap(level)`（挡"高级别配低置信"）。★ **"手段封顶"与 `missing_methods` 的关系（2026-09-17 写清）**：`missing_methods` 记的是"**该解答本该跑到、但实际未执行**"的手段（`contracts/verification.schema.json` 的定义），**"本该跑到"按适用的手段判** —— 因此**纯数值题的 `missing_methods` 通常为空**（`cross_check` 对它不适用，不算"本该跑到"），`level` 可以到 A；★ **若某一题有多种适用手段而其中一种没跑**，则 `missing_methods` 非空，按契约的 `x-invariants` **封顶到 C**（"**不跑就不能声称**"）—— 与上表的"手段封顶"同源，**不是两套规则**。

**② 逐项检查 × 结果 → 判定**（`checks[]` 的每一项都必须落到下表的某一行）：

| 检查项 | 结果 | 判定 |
|---|---|---|
| `sympy_recompute` | 与解答不一致 | **不通过** → 触发重算 |
| `symbolic_equivalence` | 不等价 | **不通过** → 触发重算 |
| `cross_check` | 与第二条路径不一致 | **不通过** → 触发重算 |
| `unit_check` | 量纲不符 | **不通过** → 触发重算 |
| **任意检查项** | **未执行**（手段缺失） | ★ **不算"不通过"，但也绝不计入"通过"** ⇒ 该报告的 `level` 按 ① 的手段封顶**下压**，且**必须在验证报告里显式列出缺哪一项**（N2："不得笼统说已校验"） |

**③ 出口（与 `§4.2-4` 一一对应）**：

| 情形 | 行为 | 对 N1 注入集的含义 |
|---|---|---|
| 全部检查通过 | 正常输出，`level` = 手段可达的最高级 | — |
| **任一项不通过** | **重算一次**（换一条策略重新求解，**上限 1 次**） | 注入的**系统错解**在这一步被拦住 |
| 重算后通过 | 正常输出，但验证报告里**如实记"重算过一次"** | 计为"被拦住" |
| 重算后仍不通过 | **标 `uncertain` + 级别降 `D` + 事件流显式告知（附未通过的检查项）** | 计为"被标注" |
| **手段缺失**（既无 `sympy_recompute` 也无 `symbolic_equivalence`） | 照常输出，但 `level` 只能到 **C 或 D**，且报告里显式列出缺失项 | ★ **这是"走了流程却一步真验证都没做"的可见化** —— 旧仓级别恒为 D，正是这个形态被写成了"验证通过" |

> ★ **无限重算被明确拒绝**：上限 1 次的理由是"重算"= **换一条策略**，而不是同一次调用的重试采样（多个样本共享同一个错误前提）。上限放开会把"验证"退化成"直到算对为止"，而 **N1 的验收恰好是"允许标注，不要求修好"**。
> ★ **本表是 `docs/01 §6`"诚实性"行的执行载体**，也是 **§9.1 注入集**断言的对象：注入的系统错解，必须落在 ③ 的"被拦住"或"被标注"两行之一。

## 5. 状态机

### 5.1 编排图状态机

```
idle ──▶ routing ──▶ running ──┬──▶ verifying ──┬──▶ done
                      ▲         │                │
                      │         │                └──▶ needs_human ──▶ hitl
                      │         │                                    │
                      └─────────┴──◀──────── resolved ◀──────────────┘
                                │
                                └──▶ failed（错误体见 §6.2）
```

**约束**：`done` / `failed` 为终态；`needs_human` **必须有超时**（否则图永远挂着）。
**已知限制（诚实）**：图检查点当前为**内存态** ⇒ **只允许单 worker**。见 §8 的失败模式表。

### 5.2 提示阶梯状态机（F6 —— 伦理约束的落地点）

```
        未作答
          │ 请求提示 1
          ▼
    hint_used=1 ──「方向」**不给完整思路**
          │ 请求提示 2
          ▼
    hint_used=2 ──「步骤骨架」**不给最终答案**
          │ 提交作答
          ▼
        已提交 ──▶ 此时才允许返回**完整解析**
          │ 错题重做（source=wrong_review）
          ▼
        重新作答（attempt_no+1，hint_used **重新计**）
```

**三条不可违反**：① 未提交前**不返回完整解析**；② 每次提示**精确 +1**（这是"如实记入掌握度"的依据）；③ 重做时 `hint_used` 重新计，但**历史不清零**（否则"我第三次才做对"的证据就没了）。

### 5.3 账号状态机（F15）

```
          创建(CLI)              禁用(管理员)
   (无) ──────────▶ active ◀───────────────▶ disabled
                     │  ▲                        │
        删除(本人/管理员) │  │ 启用(管理员)          │
                     ▼  │                        │
                  deleted ◀───────────────────────┘

   任一状态下的失败计数：failed_count≥5 ⇒ locked_until 置未来时刻（60s 后自动解除）
```

**`deleted` 是脱敏态，不是物理删除**：`username` 改为 `deleted_<8hex>`、`password_hash` 置空串（**任何密码都登不进去**）、令牌全撤；**四张学习表**（问答流水 / 提示流水 / 作答 / 掌握度）的数据**硬删**。

★ **`must_change_pw` 的自环（2026-09-16 补）**：管理员重置密码后置位 ⇒ **登录成功，但只放行 `POST /api/auth/password`**，其余学习类接口一律 **403 `must_change_pw`**（**不复用 `forbidden`** —— 它的语义是"角色不足"，混用会让前端把"去改密码"显示成"无权访问"；这与 §6.3 把"禁用"和"越权"分两个 code 是**同一条原则**）。改密成功后清位，并按 §4.1 的第 4 条**撤销该用户全部令牌**。

```
        active ──(管理员重置密码)──▶ must_change_pw=1
           ▲                                  │
           │                    （只放行 POST /api/auth/password）
           └──────────(改密成功 ⇒ 清位 + 撤销全部令牌)──────────┘
```

> **为什么不能只靠前端跳转**：管理员重置密码的**唯一意义**是"学生必须自己换一个密码"。若这个位只在登录响应里回一次、由前端决定跳不跳，那么**直接调任意学习类接口就绕过去了** —— 于是管理员**始终知道学生的密码**，重置密码反而成了一个降低安全性的功能。`must_change_pw` 必须由服务端在每个请求上判定，**这是它的全部价值**。

> **两个 `deleted` 不再同名易混**：`student_user.status = 'deleted'` 是**账号状态**（保留，脱敏态）；`student_attempt` 的软删字段**已删除**（见 §3.2 —— 它是"有读无写的死字段"）。
>
> **username 复用规则**：脱敏后原 username **可以再次被注册**（不引入"退休用户名表"），因为 `user_id` 不复用；**教师视角靠 `user_id` 后 8 位区分同名**（管理页必须显示它）。若将来发现"同名不同人"造成实际混淆，再改为禁止复用并走 ADR。

### 5.4 令牌状态机

```
issued ──▶ active ──┬──▶ expired（到期）
                    ├──▶ revoked（改密 / 禁用 / 删除 / 主动登出）
                    └──▶ orphan（账号被删除后，行被级联清理）
```

## 6. 接口与错误语义

### 6.1 路由清单（按模块）

| 模块 | 端点 | 认证 | 备注 |
|---|---|---|---|
| 系统 | `GET /api/health` | **否** | 唯一无需登录的 API；★ **只报告本地事实**：DB · **L1 缓存** · **资产 `rev`**。★ **不报"模型状态"（2026-09-16 修正）** —— 那需要一次出网调用，会与 §1.5③ 的"恰好两个口"、§8-7 的"health < 100ms"**同时冲突**；且 N14 下**不存在部署级端点**，health 无从知道任何用户的模型 |

| 身份 | `POST /api/auth/logout` · `POST /api/auth/password` | 是 | 改密后撤销全部令牌 |

| 身份 | ★ **`GET /api/me/notice` · `POST /api/me/notice`** | 是 | ★ **N15 的读写口（2026-09-16 补位）**：`GET` 返回"这次要不要告知"（**判据是去向 `egress`**，见 §1.5①）；`POST` 写 `student_user.notice_ack_at`。**此前 N15 只有字段、没有接口** —— §10 甚至把它的落点指向了 §7.1 |
| 答疑 | `POST /api/chat`（**`fetch` 流，非 EventSource**；请求头带 `X-Model-Key`） | 是 | 事件 `seq` 单调（**只用于去重，不承担断流续传** —— §4.2-1）；**无凭据 ⇒ 503 `model_key_missing`**（§6.3） |
| ★ 运行 | **`GET /api/runs/{id}`** · ★ **`POST /api/runs/{id}/hitl`** | 是 | ★ **2026-09-16 补位**：前者是 **F2 结构断言的第二处落点**（`steps: [{说明, 式子}]`，§4.2-7）；后者是 §4.2-5 要求**成对**的 `hitl.request` / `hitl.resolved` 的**应答口**。**两者此前都被正文引用，却都不在本表里。** ★ **run 生命周期已裁定（2026-09-16，决策 2A / §11.1-4）**：run **只存在于进程内存**（§5.1 的图检查点），**进程重启后 `GET /api/runs/{id}` 返回 404 `not_found`**，**不做持久化** —— 与 §4.2-1 的"服务端不做重放缓冲、断流即重新发起"自洽：客户端本来就不能靠 run 续传，因此"重启后 run 消失"是**可接受语义，不是缺陷** |
| ★ 模型 | **`POST /api/model/ping`** · `GET /api/model/providers` | 是 | `ping` 校验用户凭据（避免"填错 key 后每次答疑都失败"）；`providers` 返回预置供应商（DeepSeek / Qwen / GLM + 自定义 OpenAI 兼容） |
| 刷题 | `GET /api/problems` · **`POST /api/practice/hint`** · `POST /api/practice/grade` | 是 | 判定确定性 + 线程池；**`problems` 不返回答案**；`hint` 是提示阶梯唯一入口（F6） |

| 管理 | `GET /api/admin/students` · `GET /api/admin/users` · `GET /api/admin/audit` · `PATCH/DELETE /api/admin/users/{id}` · `POST /api/admin/users/import` | 是（**管理员**） | 一律写审计；`PATCH` 含 **重置密码**（见下） |

**四处端点差异必须写清，否则契约会各写各的**：

- `GET /api/admin/students` = **数据视图**，是 §5"教师可见"的落点；`GET /api/admin/users` = **账号管理**（角色 / 状态 / 锁定 / 令牌）。两者的人**是同一批**，但关注点不同，**不要合并成一个接口**。
  ★ **"数据视图"必须写成可判定的形状（2026-09-16 修正）**：管理员可**逐条查看**本机学生的**作答记录与掌握度计数**（允许排序与筛选）；**不产出任何跨学生的派生指标** —— 界面上**不得出现平均分、排名、分布、热力图**。原措辞写的是"班级统计"，而 `docs/01 §9` 把"跨用户聚合"列为**排除项** ⇒ **同一个词在两侧意思相反，边界就没有执行载体**；改为上面这句后，可以**对着界面点数**。
- `POST /api/admin/users/import` **只能建 `student` 角色，且不接受学号 / 姓名字段** —— 否则一个便利功能就能破掉 N6（`docs/01` 已记账，ADR-0002 §v2 增量 6）。
- ★ **`PATCH /api/admin/users/{id}` 含"重置密码"（2026-09-16 补）**：**强制下次登录改密**（`must_change_pw`）+ **撤销该用户全部令牌** + **写审计**；新密码由管理员经**单独渠道**告知学生。此前这一项在 ADR-0002 决策 3 里有、在 v2 接口清单里**悬空**。

**R-A 强制的字段**（所有请求体**与查询参数**的字符串字段必须有上界）★ **本表已补齐（2026-09-16）** —— ★ 2026-09-17 把范围写明：表头原写"**请求体**"，而表里收了**查询参数** `cursor`（§6.4 的 `?limit=&cursor=`）⇒ **范围按"所有外部输入字符串字段"判**，查询参数同样算（这比原措辞更严，与表体一致） —— 原文只有五行，而规则声称"**所有**请求体字符串字段"，**规则的范围 ⊃ 检查表**：

| 字段 | 上界 | 理由 |
|---|---|---|
| `username` | 32 | 契约正则 `^[A-Za-z0-9_.-]{3,32}$` |
| `password` | 72 字节 | bcrypt 输入上限 |
| `answer` | **200** | 旧仓 P0：无上界 ⇒ 判定被喂 100k 位数字 |
| `query` | **2000** | 答疑提问；超长直接 400 |
| `display_name` | 64 | — |
| ★ `context.text`（F1 的上下文，可含教材片段） | **4000** + **嵌套深度 ≤ 3** | ★ **比 `query` 更危险**：它是**常用路径**（F1 明确要求无上下文时显式降级），也是**最容易被塞进大对象**的参数（`{"text": "<1MB>"}`） |
| ★ `session_id` | 64 | 出现在 `hint` 与 `grade` 两处 |
| ★ `item_id` | 64 | 同上 |
| ★ `cursor` | 256，**且必须校验可解码** | 不校验就是一个**注入面** |
| ★ **`base_url`**（N16 的端点） | **2048**，且 **`http(s)` 白名单 + 主机校验**：必须 `https`（**仅单机形态的 loopback 例外**）· **禁 RFC1918 / 169.254.169.254 等内网与元数据地址** · **禁跟重定向** | ★ **这是 SSRF 的输入面**：§4.2.1 的六条信任边界要施加的**就是它**，而它此前**不在这张表里**（表声称覆盖"所有请求体字符串字段"） |
| ★ **`provider`** | 32，**枚举**（预置供应商 + `custom`） | 非枚举值会让"预置白名单"这条规则形同不存在 |
| ★ **`model`** | 128，**字符集受限**（不得含控制字符 / 路径分隔符） | 它会拼进上游请求的 body，不做字符集约束就是一个注入面 |

> ★ **"静态扫描"的实现方式必须写明**（否则门禁本身不可 review —— 这与 §9 对运行器"必须可 review"是同一条标准）：扫描**请求体模型的字段声明**（Pydantic 层），断言**每个 `str` 字段都带 `max_length`**；对正则，断言判定类正则**不含嵌套量词**（`(...)+` / `(...)*` 内部再有量词）。

### 6.2 统一错误体（`error.schema.json` —— 旧仓的缺口之一）

```json
{
  "error": {
    "code": "unauthenticated",
    "message": "未登录或登录已过期，请重新登录",
    "detail": { "field": "password", "reason": "too_short" }
  }
}
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `code` | **机器读的稳定标识**（枚举，见 §6.3） | 只增不改；新增须走契约变更 |
| `message` | **给人看的中文说明** | 不含内部路径 / SQL / 堆栈 |
| `detail` | **可选**结构化补充（哪个字段错了、缺什么） | 不得放敏感值 |

**为什么要有它**：旧仓每个接口各写各的形状（有时是字符串，有时是对象，有时干脆是 500），前端只能按形状猜。**统一错误体是前端能写出一套错误处理的前提**。

### 6.3 状态码与 `code` 语义表

| HTTP | `code` | 触发条件 | 前端行为 |
|---|---|---|---|
| 400 | `invalid_argument` | 参数校验失败（含超长、格式） | 高亮字段 + 显示 `message` |
| 401 | `unauthenticated` | 无令牌 / 令牌无效 / 已过期 / 已撤销 | **清本地令牌 + 跳登录** |
| 401 | `bad_credentials` | 登录时用户名或密码不正确 | 显示提示，**不清空用户名** |
| 403 | `forbidden` | **非管理员访问 `/api/admin/*`**（角色不足） | 显示"无权访问"，**不跳登录** |
| ★ 403 | **`must_change_pw`** | **管理员重置密码后、改密前访问任何学习类接口**（F15 · §5.3） | **强制跳设置页改密**；★ **不清本地令牌**（令牌本身有效） |
| 403 | `account_disabled` | 账号被禁用（**仅在密码验证通过之后可能出现**） | 显示"账号已停用，请联系老师" |
| 404 | `not_found` | 资源不存在，**含"存在但不属于我"的资源**（故意不区分） | 友好提示 |
| 409 | `conflict` | 用户名已存在 | 提示换一个 |
| 423 | `locked` | 连续失败过多，短时锁定（**仅在密码验证通过之后可能出现**） | 显示剩余秒数 |
| 500 | `internal_error` | 未预期错误 | 显示"服务出错"，**附 trace id** |
| 503 | `dependency_unavailable` | ★ **运行期**不可恢复的依赖故障（如 L2 库文件在运行中变得不可读写、磁盘满）。★ **不含语料缓存** —— 缓存缺失**有降级路径**（§8-13b：如实返回"出处暂不可用"）。★★ **2026-09-17 二次改正**：上一版写的触发条件是"**L0 内容资产加载失败**（与 §8-14 同一模式）"，而 §8-14 规定那七条**启动即报错退出** —— **进程根本不存在，HTTP 503 发不出来** ⇒ 这一版**又把它写成了死枚举**（正是它上一版自称要修的毛病）。**边界现在写死**：**启动期检查失败 = 进程不启动（无响应可言）**；**运行期依赖故障 = 503 `dependency_unavailable`**。它**不是**容量超限（那是 `server_busy`，2026-09-16 已拆出） | 显示"服务处于降级模式" |
| ★ 503 | **`server_busy`** | ★ **新增（2026-09-16）**：**并发答疑超过承诺上限**（**第 11 路起**，N20 · §8-13g）。★ **此前没有任何"容量超限"的 `code`**，只能复用 `dependency_unavailable` ⇒ 前端会显示"服务处于降级模式"，而真实含义是"**同时答题的人太多，稍后重试**" —— 与"断网被推去填 key"**同型的误导**（用户动作完全相反）。★ **命名把责任划在我们这一侧**：叫 `capacity_exceeded` / `too_many_requests` 会被读成**限流或配额**，而 `model_quota_exceeded` 是**用户自己的模型额度**，两个名字相近会让前端分支与排障分类都混 | 显示"**当前同时答题的同学较多，请稍后重试**"；**可重试**；**不清本地令牌、不引导填凭据、不显示"降级模式"** |
| ★ 503 | **`model_key_missing`** | **未配置凭据**（N14） | 显示"**未配置模型凭据**"并提供 `#/settings?tab=model` 入口；**判定 / 错题本 / 进度 / 知识图谱照常可用** |
| ★ 503 | **`model_unreachable`** | **端点不可达 / 超时 / 被信任边界拒绝**（N14 · N16 · §4.2.1） | 显示"**网络或模型服务不可达，可重试**" —— ★ **不得引导去填凭据**；★ **不得清本地登录令牌** |
| ★ 400 | **`model_key_invalid`** | 用户凭据无效 / 被撤销 | 提示到设置页重填；**不得清本地登录令牌** |
| ★ 402 | **`model_quota_exceeded`** | 用户凭据额度不足 / 欠费 | 提示"你的模型额度不足"，并说明**费用由凭据持有人承担** |

> ★ **凭据类错误绝不能复用 401（2026-09-16 新增，本轮最容易踩的坑）**：前端收到 `401` 的既定行为是"**清本地令牌 + 跳登录**" —— 若把"模型 key 填错"也标成 401，用户会**被登出**，而真正的问题是设置页里那串 key。因此这些 `code` **必须是独立值**（503 `model_key_missing` / 503 `model_unreachable` / 400 `model_key_invalid` / 402 `model_quota_exceeded`），且 `model_key_invalid` 用 **400** 而非 401：它是**客户端可修的输入问题**，不是身份问题。

> ★ **`model_unavailable` 已按 `ADR-0005 §5` 拆为两个 `code`（2026-09-16）**：原表的触发条件写"未配置凭据、**供应商不可达**"、前端行为写"显示'未配置模型凭据'并提供设置页入口" —— 于是**断网的学生被推去填 key**，而两者要的用户动作**完全相反**（一个去填、一个去重试）。ADR 已裁定，本篇此前是合并的，现已落齐（§4.2.1 · §6.1 · §8-13 同源）。

> **越权只走一条路，不再两处定义**（本轮收口）：**读他人数据 → 404**（对外看起来"不存在"，避免用状态码探测他人 ID 是否存在；**日志里记 403** 便于排查）；**403 `forbidden` 只保留"角色不足"**，即非管理员访问 `/api/admin/*`。
> ✅ **已裁定（2026-09-16，负责人）**：旧仓把"账号被禁用"与"权限不足"都归 403 且用同一段文案；**本仓分成两个 `code`**，理由是用户需要知道"这是账号问题，去找老师启用"而不是"我权限不够"。
> **已考虑并否决的替代方案**：退回单一 `forbidden`（理由是避免泄露"该账号存在且被停用"）。
> **否决依据已从"经验判断"改成一条可断言的不变量**（评审 A3 指出原表述不成立，已修）：**在密码通过之前，一切失败都返回同一个 `401 bad_credentials`，且都烧等长的时间**（`§4.1`）。因此 `403 account_disabled` 与 `423 locked` **只可能在密码验证之后出现** —— 攻击者拿不到密码就看不到这两个状态，**不构成额外的账号枚举面**。这条不变量由登录用例直接断言（见 §8）。

### 6.4 分页口径（旧仓的第二个缺口）

**统一为 cursor 分页**，不用 `offset`：

```
请求：?limit=20&cursor=<opaque>
响应：{ "items": [...], "next_cursor": "<opaque>|null" }
```

| 规则 | 值 |
|---|---|
| `limit` 默认 / 上界 | 20 / **100**（超界即 400，不静默截断） |
| `cursor` | 不透明字符串（内部是 `created_at` + `id` 的编码），**客户端不得解析** |
| 排序 | 一律 `created_at DESC, id DESC`（稳定序，避免同秒记录乱序） |

**为什么不用 offset**：问答流水与作答记录是**追加写**的表，翻页时新记录插入会让 offset 漂移 ⇒ **同一条记录被读到两次、或某条被整页跳过**。这对"错题本复习"是真实伤害。

### 6.5 SSE 帧

帧格式与 14 类事件由 `events.schema.json` 定义（A3）。本仓对**帧的两条增量要求**：

1. **每帧带 `seq`（单调递增整数）** —— ★ **只用于去重，不承担"断流续传"**（服务端**不做重放缓冲**，断流语义是**重新发起**，见 §4.2-1）。**原写"断流续传与去重的唯一依据"，与 §4.2-1 直接冲突，2026-09-16 统一**。
2. **终帧必须显式**（`done` 或 `error`）—— 让前端能区分"跑完了"与"网断了"，否则只能靠超时猜。

### 7.1 URL 可寻址设计（N11 —— 旧仓实测返回键失效）

**规则**：**凡是有意义的界面状态，必须由 URL 表达**。顺序是"URL 是状态源，组件是它的投影"，不是反过来。

| 路由 | 表达的状态 | 为什么必须可寻址 |
|---|---|---|
| `#/login` | 登录页 | — |
| `#/home` | 首页 | — |
| `#/practice?kc=kc_bayes&item=prob_0012&hint=2` | **具体题目的具体提示层级** | "刷到第 3 步提示"要能刷新、能分享、能回退 |
| `#/wrong?kc=kc_bayes&cursor=<opaque>` | 错题本 + 知识点筛选 + 翻页位置 | 复习到一半刷新不能回到起点 |
| `#/knowledge?kc=kc_bayes&view=graph` | 知识点定位 + 视图模式 | 分享"就是这个知识点不会" |
| `#/admin?tab=students&user=usr_xxx` | 管理页标签 + 选中学生 | 管理员排查时要能把链接发给别人 |
| ★ `#/settings?tab=model` · `#/settings?tab=notice` | **模型端点与凭据**（N14 · N16）· **外传告知**（N15） | ★ **2026-09-16 补位**：§4.2.1 / §6.3 / §8-13 **三处都指向 `#/settings?tab=model`**，而本表**此前没有这一行**；设置页是 **N14 / N15 / N16 三联的承载页**，缺它则 **N11 的"可寻址完备清单"不可能通过** |

**三条实现要求**：
① 监听 `hashchange` **与** `popstate`（旧仓只写 hash、无人监听 ⇒ 返回键只变 URL 不变视图）；
② 视图状态从 URL **单向派生**，组件不得各存一份；
③ ★ **URL 是渲染状态的来源，不是权限或计数的来源** —— `hint=2` 只决定"界面显示到第几级"，**提示次数一律以服务端 `hint_log` 为准**（F6）。手工把 `hint` 改成 2 不会让服务端认为已取过提示，也不会让解析提前出现。

★ **落地页约定（2026-09-27 补 —— 此前本表**没有**说过空哈希落在哪）**：**空哈希（首次打开站点 `/`）⇒ 落到 `#/home`**。★ 由**外壳**执行（`core/router.js` 的兜底只广播提示、**不做重定向** —— 重定向是外壳的决定），实现见 `frontend/index.html` 的启动段。★ **为什么必须写下来**：没有这一条时，首次打开会停在**"未知页面"**（2026-09-27 用真实浏览器实测发现：`location.hash` 为空 ⇒ `router` 归一成 `/` ⇒ 没有 `/` 这条路由 ⇒ 兜底页）。这类缺陷**静态门禁与 `[SKIP]` 都看不见** —— 它属 ADR-0006 判给"人工"的那一半。

### 7.3 样式分层（**单一令牌源**）

### 7.4 状态管理的边界

| 状态 | 存哪 | 为什么 |
|---|---|---|
| 令牌（键名 `dsh.token`） | `localStorage` | 免构建、无后端渲染；XSS 风险由"不用 `innerHTML` 拼用户内容"控制（**R-E 是唯一防线，且它是纪律不是机制**） |
| 界面位置（知识点 / 题目 / 提示层级 / 翻页） | **URL** | N11：可刷新、可分享、可回退 |
| 跨页面临时态（当前 run、未提交的作答） | `core/store`（内存） | 刷新即丢是**可接受的** —— 它们本来就不该是持久状态 |
| ★ **模型凭据（N14）** | `localStorage`，键名 **`dsh.model_key`** | 只存浏览器、随请求携带（`X-Model-Key` 头）；**服务端不落任何介质**。★ 它**不进 §7.4 之外任何一处的"存哪"清单**，其清除动作由 §1.4 的第 5 条统一定义 |
| ★ **端点配置（N16）** | `localStorage`，键名 **`dsh.endpoint`**（`provider` · `model` · `base_url`） | 与凭据**同生命周期**；`base_url` 同时是 §4.2.1 六条信任边界的输入面 |
| 持久学习数据 | **只在服务端** | 单一真相；避免前后端两套数据打架 |

## 8. 失败模式与降级（一开仓就定死，不留给日后踩）

| # | 场景 | 设计行为 | 谁守（测试） |
|---|---|---|---|
| 1 | **未登录 / 令牌过期** | 401 `unauthenticated`；前端清令牌并跳登录 | 接口测试 |
| 2 | **令牌被撤销**（改密 / 禁用 / 删除） | 立即 401（**不是等 7 天**） | 接口测试 |
| 3 | **越权读他人数据** | 404（对外）· 403（日志） | 越权用例 |
| 4 | **账号禁用 / 锁定** | 403 `account_disabled` / 423 `locked`；两者**只能出现在密码验证通过之后** | 接口测试 |
| 4b | ★ **登录失败的信息量不变量** | **密码通过之前一切失败都是同一个 401 `bad_credentials`，且响应耗时同量级** —— 断言"不存在的用户"与"密码错误"返回**同一状态码 + 同一 code**，且"已禁用/已锁定账号 + 错误密码"**也不泄露**其存在 | 登录用例（枚举面回归） |
| 5 | **超长输入** | 400（有上界）；**绝不进入判定** | R-A 扫描 + 长度用例 |

## 9. 评测资产的存放与执行（N13 · 盲测）

A1 已定（本轮回补时同步细化）：**样例集与运行器入仓并纳入门禁（防退化）· 冻结正式集由非实现者保管、不入主仓（能力验收）**。本篇给出可执行形式：

> ★ **理由已换锚（2026-09-16）**：原文写的是"**离线、无密钥基础设施的前提下（ADR-0001），门禁无法从仓库外取题**" —— 那个前提**已不成立**（v2 联网、且用户自持凭据，理论上可以联网取题）。**结论不变，理由改成**：为一件**用一次**的验收，引入**外部托管位置 + 一套取题凭据**，成本高于收益；而"**正式集不进仓**"这条隔离要求**与能不能联网无关**。

| 资产 | 存在哪 | 谁写 | 谁执行 | 自动化 |
|---|---|---|---|---|
| **样例集**（3–5 题 + 期望结论） | **`content/eval/sample/`**（**入仓**） | 非实现者 | 本地门禁（接远端后即 CI） | ✅ 自动红灯 |
| **运行器** | `scripts/eval_verify.py --frozen-dir <dir>`（**入仓，不含任何答案**） | 任意人 | **任意人**（★ 2026-09-17 改正：原写"非实现者"，与 `docs/01 §6` 的"**谁执行 = 任意人**（**正式集的执行结果只能由非实现者签署**）"**两表口径不一** —— 正确口径是**执行与签署分开**：谁跑都行，**结论只能由非实现者签**，见本节末的注） | — |
| **冻结正式集**（注入集 20 道 + 冻结验证集） | 主仓**之外**（非实现者本机） | 非实现者 | 非实现者 | ❌ 人工门禁 |
| **期望判据表** | 与正式集同处，**不入主仓** | 非实现者 | — | — |

> ★ **"主仓之外"从 2026-09-18 起不再只靠人**：上面两行的落点在 `.gitignore` 里是 **deny-by-default**（`frozen/` · `frozen/**` · `frozen_cases.json` · `frozen_judgement.json`，任意层级匹配），与 `backend/data/**` 同属 `docs/03 §2` 规则 1 的那条安全属性 —— **"结构上不可能入库"，不是"小心别提交"**。★ **为什么必须补**：`.gitignore` 对 `content/` 一向是**显式反转放行**（`!content/` `!content/**`），所以任何新建的 `content/eval/<任意名>/` 都会被正常跟踪；而**远端仓库是 public**（实测），误提交一次**历史与 fork 里都删不干净**。★ 入仓的**只有** `content/eval/sample/`（样例集），上述规则**不碰它**。

**为什么把"评分脚本"拆成"运行器 + 期望判据表"**：运行器本身**必须可 review**（否则没法确认它真的在数命中，而不是在数"没报错"）。把**答案**移出仓库、把**机制**留在仓库，两个目的同时达成。（该细化已同步回 `docs/01` 的 N13 与附录 B.2。）

★ **执行交接（2026-09-16 补，否则这条门禁没有可执行的路径）**：**执行者在自己的仓库副本上运行**，冻结集**始终留在主仓之外**：

```
非实现者：把冻结集与判据表放在自己机器的任意目录（不入仓、不进 PR）
执行者：  git clone <本仓> → scripts/eval_verify.py --frozen-dir <该目录>
            → 输出 日期 / 执行人 / content_rev / 逐类命中数 / 结论
```

> ★ **"函数级、确定性、可批量"描述的是运行器，不是门禁**：它可以一次跑完 20 道，但**结论必须由非实现者签署** —— 自动化与盲测是两件事，混着写会让下一轮以为"既然可批量，那就进 CI 吧"。

16. ★ **门 B 的回归基线依赖门 C 才执行的冻结验证集（2026-09-17 独立审计发现）**：`docs/06 §4` 第 6 项要求"**首次全量测量值于阶段门 B 结束时**录入 `docs/01 §6` 并冻结"，而 `docs/01 §6` 的两条基线（解题正确率 / 判定准确率）写的是"**在冻结验证集上**"—— 冻结验证集属**冻结正式集**，其执行被四处写死在**阶段门 C**（`docs/01` N13 格 · 本文 §9.1 · `docs/05 §6` · `docs/03 §8.2`），且**不入仓、由非实现者保管**。⇒ **门 B 在字面上过不去**：要么它永远不满足，要么有人提前把正式集跑掉、把"阈值不得在看到结果后调整"的隔离作废。**须裁定**（不是文档自洽能定的）：建议把 **B 门基线的测量集**与 **C 门的冻结验证集****分开写清**（例如 B 门用**自制开发集**、C 门才用冻结集），并同步 `docs/01 §6` 的测法措辞。
17. ★ **删除权与备份冲突（同轮发现）**：F16 声明"删除权覆盖**服务器上属于该用户的全部数据**"，边界句只列了"第三方已收到的请求"；而 N19 的备份落在**我们自己机器**上、含该用户被删的全部行、**恢复演练会把它们原样复活**，且**删除动作不清备份**；`deleteResult` 也只有 `logs_in_scope` 一个边界字段。⇒ 与 R-O 当年堵的"**验收通过但数据仍在**"同型（日志堵了，**备份没堵**）。**须裁定**：删除时清备份 / 给 F16 补边界句 + 契约加字段 / 把备份保留期压到与删除承诺相容（第 14 条的保留策略是同一处）。
18. ★ **提示第 3 级的可取判据被放宽（同轮发现）**：F6 与 §4.3-3 / §5.2 写的是"**本次未提交前不得返回完整解析**"，而 `contracts/hint.schema.json` 的 `x-invariants` 写的是"**该 `(user,item)` 已有任一次作答即可**"。`hint_used` 的作用域是 `(user,item,session)`，且 §5.2 明写"错题重做时 `hint_used` **重新计**" ⇒ **重做一道做过的题时，新会话里连点三次即可在本次未提交的情况下拿到完整解析** —— 伦理约束（"把抄答案变成要点两下"）在这条**正常路径**上被绕过，而门 B 的 F6 用例在新账号上仍是绿的、看不见它。**须裁定**：契约的 invariant 收紧为"**本次会话已提交**"，还是承认"做过就能给"是有意放宽。
19. ★ **N4（零 npm / 零安装）与"前端冒烟断言 DOM"的前提冲突（同轮发现）**：N8 用"**真算渲染对比度必须用无头浏览器，与"零安装"前提冲突**"这条理由**砍掉**了对比度渲染的自动化；而 **R-F ①② · R-G · R-I** 都被写成"**可自动**"，其中 **R-I 是 F3（MUST）"后端发了前端不看等于没发"的唯一载体**，`docs/06 §8` 也承认这三条"**需要真跑前端**"。⇒ 同一前提在一处被用来砍自动化、在另三处被无视 —— **两条声明里必有一条为假**。**须裁定**：要么承认测试环境允许浏览器（那 N8 的排除理由要改），要么把这三条从"可自动"降级为"人工 review"，并另找 F3 的载体。

20. ★ **查询参数没有契约形状（2026-09-17 独立审计发现）**：契约覆盖的是**请求体与响应体**，而 §6.4 的 `?limit=` / `?cursor=`、`GET /api/knowledge/formula` 的**检索名**、以及管理页的**筛选参数**都**只有散文口径、没有形状**；§6.1 的 **R-A 字段表**却收了查询参数 `cursor` ⇒ **"哪些输入算外部输入"这一层没有唯一真相**（R-A 的范围本轮已写明为"所有外部输入字符串字段"，但**形状**仍缺）。**落点建议**：把查询参数并入 `pagination.schema.json`（分页类）与各自的契约（检索类），或在 `docs/04 §3` 的覆盖表里**显式声明"查询参数不进 v2 契约"**并给出理由 —— **两条路都行，但要选一条**，否则"契约零悬空"这句话在查询参数上不成立。
